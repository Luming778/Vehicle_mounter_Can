# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A multi-node vehicle control system using three STM32F103 microcontrollers communicating over CAN bus. Supports local button control, voice control, and remote WiFi/MQTT control. Documentation is primarily in Chinese.

## Build System

**Keil MDK-ARM V5 (uVision 5)** — no Makefiles or CMake. Each sub-project is an independent Keil project compiled with ARMCC V5.06.

| Sub-project | Keil Project | Target MCU |
|---|---|---|
| `Vehicle_module_controller_1/` | `MDK-ARM/car_test2.uvprojx` | STM32F103C8Tx (64KB Flash, 20KB RAM) |
| `Vehicle_module_controller_2/` | `MDK-ARM/Led_Button_.uvprojx` | STM32F103C8Tx (64KB Flash, 20KB RAM) |
| `Vehicle_screen_controller/` | `MDK-ARM/CAR.uvprojx` | STM32F103ZETx (512KB Flash, 64KB RAM) |
| `1/` | `MDK-ARM/1.uvprojx` | STM32F103C8Tx — bootloader for node 1 OTA |
| `2/` | `MDK-ARM/2.uvprojx` | STM32F103C8Tx — bootloader for node 2 OTA |

Peripheral init code is generated by STM32CubeMX (`.ioc` files). Custom logic goes in `/* USER CODE BEGIN */` / `/* USER CODE END */` blocks. There is no CLI build — open `.uvprojx` in Keil to build/flash/debug.

## Architecture

Three-node distributed system on a shared CAN bus (166.67 kbit/s):

- **Vehicle_module_controller_1** — Bare-metal superloop. Controls car lights, windows, sunroof. 4 keys + 4 LEDs + OLED. CAN TX ID `0x666`, RX filter `0x7BF`.
- **Vehicle_module_controller_2** — Bare-metal superloop. Controls car doors. 1 key + OLED. CAN TX ID `0x555`, RX filter `0x7BF`.
- **Vehicle_screen_controller** — Master node running FreeRTOS (CMSIS-RTOS V2, heap_4, 8KB heap). Drives OLED display, voice module (USART2), ESP8266 WiFi (USART3 + DMA), MQTT client. CAN accepts all messages (mask `0x0000`), dispatches via interrupt → FreeRTOS queue.

## OTA / Bootloader Architecture

The system supports CAN-bus OTA firmware updates. `app_rec/` is the reference OTA sender implementation; `1/` and `2/` are bootloaders for the two device nodes.

### Memory Layout (screen controller)

| Region | Address | Size | Purpose |
|---|---|---|---|
| Bootloader (reserved) | `0x08000000` | 48KB | Future bootloader |
| Application | `0x0800C000` | 464KB | screen_controller app |

External storage: W25Q32 (SPI2) for firmware staging, W24C02 (I2C1) for upgrade flag at address `0x10`.

### OTA Module Layering

```
app_update.c/h          ← OTA state machine (do not modify)
can_bus.c/h  │  storage.c/h    ← Functional modules (do not modify)
can_adapter.c │  storage_adapter.c  ← Adaptation layer (modify per target)
Int_can.c │ Int_w25q32.c │ Int_w24c02.c  ← Low-level drivers
```

Porting guide: `app_rec/porting-guide.md`. Design spec: `docs/superpowers/specs/2026-05-31-ota-porting-design.md`.

### CAN FIFO Isolation for OTA

| FilterBank | CAN ID | FIFO | Purpose |
|---|---|---|---|
| 0 | 0x666 (exact) | FIFO0 | App logic (node 1) |
| 1 | 0x0020 (mask 0xFFE0) | FIFO1 | OTA firmware data |
| 2 | 0x555 (exact) | FIFO0 | App logic (node 2) |

The first matching FilterBank wins. If FilterBank 0 uses mask `0x0000` (accept all), it intercepts everything and FIFO1 never receives data.

## CAN Protocol

4-byte data frames: `{header_byte1, header_byte2, cmd, extra}`

- Screen → nodes: `{0xAA, 0x11, cmd}` on CAN ID `0x77F` (node 1) / `0x7BF` (node 2)
- Nodes → screen: `{0x13, 0x24, cmd, extra}` on CAN ID `0x666` (node 1) / `0x555` (node 2)

Commands: `0x01`=lights ON, `0x02`=lights OFF, `0x03`=windows ON, `0x04`=windows OFF, `0x05`=sunroof ON, `0x06`=sunroof OFF, `0x07`=door OPEN, `0x08`=door CLOSE.

## Code Organization (per sub-project)

```
Core/                    ← CubeMX-generated (main.c, stm32f1xx_it.c, freertos.c)
Drivers/
  STM32F1xx_HAL_Driver/  ← ST HAL library
  CMSIS/                 ← ARM core headers
  Peripheral_Driver/     ← Custom abstractions (driver_key, driver_led, driver_can, driver_oled)
  hardware/              ← OLED driver (SSD1306), circle_buffer (screen controller only)
  bootloader/            ← OTA module (screen controller only)
Middlewares/              ← FreeRTOS + mqttclient library (screen controller only)
```

Bootloaders (`1/bootloader/`, `2/bootloader/`) follow a different structure: `app_bootloader.c` (state machine) + `Int_bootloader.c` (low-level flash/storage drivers).

## FreeRTOS Tasks (screen controller only)

Created in `freertos.c` → `MX_FREERTOS_Init()`:
- `oled_task` (pri 15) — reads `can_rx_queue`, updates display
- `can_task` (pri 13) — heartbeat LED on PB5
- `AT_Parse` (pri 15) — parses ESP8266 AT responses
- `MQTT_Task` (pri 15) — MQTT connect/subscribe/publish, broker at `10.60.14.76:1883`
- `voice_task` (pri 14) — reads `voice_rx_queue`, forwards as CAN commands
- `ota_task` (pri 20) — self-suspends on creation, wakes on USART1 "update" notification, suspends all other tasks during OTA

## Known Pitfalls

- **printf crashes on bare-metal nodes**: Must enable MicroLIB in Keil and add `fputc` redirect to USART1. Without it, full-run halts at hardfault.
- **CAN not receiving**: Forgot to call `HAL_CAN_Start(&hcan)` before filtering.
- **FreeRTOS tasks not running**: Total heap too small — increase `configTOTAL_HEAP_SIZE` if `xTaskCreate` returns `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`.
- **DMA/UART init order on screen controller**: USART3 DMA interrupt must be enabled *inside* the FreeRTOS task, not before `osKernelStart()`, because the AT parse task handle doesn't exist yet during `main()` init.
- **ESP32-12F vs ESP-01S AT commands**: The MQTT code was written for ESP-01S. ESP32-12F has different AT command syntax — verify module型号 before flashing.
- **vTaskSuspend(NULL) means suspend yourself**, not skip. Passing a NULL task handle to `vTaskSuspend()` is equivalent to `vTaskSuspend(NULL)`.
- **vTaskSuspend cannot be woken by vTaskNotifyGiveFromISR** — use `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` instead if you need ISR-triggered wakeup.
- **HAL_UARTEx_ReceiveToIdle_IT does not null-terminate** — manually add `\0` in the callback before calling `strstr()`.
- **W25Q32 wait_busy needs timeout** — the SPI flash busy-wait loop has no timeout; add `HAL_GetTick()` guard to prevent infinite hangs.
